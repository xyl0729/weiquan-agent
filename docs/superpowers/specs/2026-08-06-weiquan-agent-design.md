# 维权作战 Agent 设计说明

状态：已批准  
来源：`D:\agent development\PLAN.md`  
数据准备方式：方案 A，由 Codex 从官方来源逐条整理，用户最终人工确认。

## 产品边界

本项目把押金、预付卡、加班费、退货等日常纠纷整理成可执行的维权行动方案。
它提供信息整理与文书辅助，不构成法律意见，不预测个案结果。

三条不可突破的边界：

1. 法条零生成。条号、正文、生效日期和来源只能来自可核验的官方资料。
2. 判断由可审计的 playbook 规则给出，LLM 不负责形成 verdict。
3. 输出首先展示需要立即固定的证据，大额或复杂纠纷提示咨询执业律师。

## v1 架构

- FastAPI 提供咨询、追问、进度页和健康检查接口。
- SQLite 保存法条、短期会话、进度、限流和支出流水。
- SQLite FTS5 负责本地全文检索；v1 不引入向量库或重型 Agent 框架。
- Anthropic API 仅用于场景分类、槽位抽取和有限的话术润色。
- Playbook YAML 保存槽位、规则、法条引用、证据清单和升级步骤。
- Jinja2 模板负责确定性生成沟通话术和文书草稿。
- 单页 HTML 与原生 JavaScript 提供用户界面。

主流程固定为：分类、抽取、强制召回、规则求值、辖区规则、时效计算、方案渲染、
进度记录。模型不能改变步骤顺序或任意选择工具。

## 数据流

1. 用户提交口语描述，后端按 playbook 列表分类。
2. 后端抽取已声明槽位；缺失必填项时直接使用 playbook 中的 `ask` 追问。
3. 信息齐全后，按 `legal_basis.ref` 精确取回官方法条，并用 FTS5 补充检索。
4. 受限表达式求值器按顺序执行规则，首个命中项给出 verdict。
5. 确定性函数计算辖区提示和剩余时效。
6. 模板生成行动步骤，LLM 只能润色非法律事实性的表达。
7. 会话短期保存，过期删除；方案通过不可枚举 token 提供只读访问和手动进度更新。

## 法律数据工作流

Codex 可以从国家机关官方网站逐条摘录候选数据，但不能把自己的检查视为人工核验。
每条候选记录必须包含法律全称、简称、条号、数字序号、原文、生效日期和官方来源链接。
候选数据在用户确认前保持 `placeholder_data: true`，不得用于真实咨询。

用户通过核验清单确认全部记录后，才将数据标记为已核验并执行入库。检索评测集至少
包含 50 条人工确认的口语查询与预期引用；`Recall@5` 达到 0.90 后才可越过数据门禁。

不编写抓取脚本，不依赖裁判文书网站，不生成或猜测法律规则、条号和案件结果。

## 错误与安全

- playbook 引用无法精确命中时启动失败，不静默跳过。
- 必填槽位缺失时最多追问两轮，此后只输出保守的“信息不足”方案。
- 规则表达式使用 `simpleeval` 白名单，禁止 `eval()` 和 `exec()`。
- API Key 只从请求头或环境变量读取，不入库、不落日志。
- 用户自带 Key 绕过服务端配额；服务端 Key 受每日 IP 限流和支出熔断保护。
- 会话默认 72 小时后删除，不在 v1 引入账号或推送系统。

## 验收

- 官方法条候选数据经用户逐条确认。
- 至少 50 条召回评测，`Recall@5 >= 0.90`。
- 8 个 playbook 全部通过 schema、引用和规则分支测试。
- 押金与加班场景分别覆盖民事和劳动仲裁流程差异。
- 三种 Key 模式、限流、熔断、时效边界和表达式注入测试全部通过。
- 从一句用户描述到追问、完整方案、文书和进度页的浏览器流程可演示。

## 实施顺序

1. 固化仓库基线和离线法条检索。
2. 整理、人工确认并通过真实数据门禁。
3. 打通押金 playbook、会话追问和方案渲染。
4. 用加班场景验证 schema 通用性，再扩展其余六个场景。
5. 完成限流、熔断、只读进度页和 Web 界面。
6. 执行完整自动化测试和桌面、移动端浏览器验收。
