# PostgreSQL 生产备份客户端兼容修复设计

## 背景

生产数据库运行 `postgres:16.4-alpine`，当前应用镜像
`weiquan-agent:2026.08.11-4` 基于 Debian Bookworm 安装未指定主版本的
`postgresql-client`，实际得到 `pg_dump 15.18`。`pg_dump` 不能导出主版本高于
自身的 PostgreSQL 服务端，因此真实备份在导出阶段报
`server version mismatch`。

已确认失败发生在加密和 OSS 上传之前。应用与数据库容器仍健康，数据库卷没有被
删除或修改，OSS 中也没有本次失败产生的备份对象。

## 方案选择

保留 PostgreSQL 16.4 服务端和现有数据库卷，在应用镜像中安装明确指定主版本的
`postgresql-client-16`。不采用以下替代方案：

- 不将数据库降级到 PostgreSQL 15，因为当前卷已由 PostgreSQL 16 初始化，降级
  既不兼容也会引入数据风险。
- 不把导出、加密和上传拆到不同容器，因为跨容器传递明文备份会扩大改动范围，
  也会增加临时文件、管道失败和凭据边界的复杂度。

新版本号为 `20260811-5`。数据库镜像、数据卷、OSS 配置、域名、Nginx、端口
`8000`、另一个小程序和用户 VPN 均不变。

## 镜像与版本契约

应用镜像继续使用现有 Python Bookworm 基础镜像，通过 PostgreSQL 官方 Debian
软件源安装 `postgresql-client-16`，不再安装未指定主版本的
`postgresql-client`。构建阶段执行版本断言，只有 `pg_dump` 主版本为 16 时镜像
才能构建成功。

备份脚本在创建明文临时文件前读取客户端主版本和服务端
`server_version_num`。两者必须同为 16；否则立即输出不含凭据的
`backup_failed category=postgres_version_mismatch` 并退出。该检查位于
`pg_dump`、加密和上传之前，防止以后镜像或数据库升级时再次出现模糊失败。

## 备份数据流

兼容性检查通过后，继续沿用现有安全顺序：

1. `pg_dump --format=custom` 将明文仅写入容器 `/dev/shm`。
2. `age` 使用公开接收者加密，随后删除明文。
3. 对加密文件生成并验证 SHA-256 校验和。
4. 将加密文件和校验和上传到私有 OSS。
5. 执行现有日备份、周备份和 28 天轮换策略。
6. 全部成功后才更新 `last-success.json`。

任何步骤失败都保持当前清理 trap，不输出数据库口令、OSS 凭据、备份正文或环境
变量值。

## 测试与发布

自动化测试覆盖以下契约：

- Dockerfile 明确安装 `postgresql-client-16`，并在构建时断言主版本为 16。
- 兼容性检查发生在临时文件创建和 `pg_dump` 之前。
- 客户端或服务端主版本不为 16 时，脚本以明确类别失败，且不执行导出、加密或
  上传。
- 版本一致时，原有导出、加密、校验、上传和轮换顺序不变。
- 生产 Compose 仍使用 `postgres:16.4-alpine`，应用仍仅绑定
  `127.0.0.1:8001`。

先在本地运行备份契约、部署契约和全量测试，再生成固定版本发布包。服务器端先
上传并构建镜像，只验证镜像内 `pg_dump` 为 16，不切换应用、不运行真实备份。

真实 OSS 备份属于独立操作。即使此前失败尝试获得过批准，修复后重试前仍需用户
再次明确确认。确认后运行部署流程，使新镜像完成部署前备份、应用切换和冒烟
检查；备份成功并核对 `last-success.json` 后，才启用
`weiquan-backup.timer`。

## 失败与回滚

镜像构建或版本检查失败时，保留当前 `20260811-4` 应用和 PostgreSQL 16.4
数据库，不触发备份、不切换服务。部署后应用冒烟检查失败时，沿用现有应用镜像
回滚流程；数据库镜像和数据卷不回滚、不删除。

真实备份失败时不启用定时器，保留应用与数据库健康运行，并仅根据无敏感内容的
失败类别继续排查。备案通过前继续保持公网 Nginx `80/443` 未启用。
