# 邮箱数字验证码与 Provider 安全降级设计

## 状态

用户已于 2026-08-15 确认采用本设计的推荐方案。

## 背景

当前注册验证邮件使用点击链接。首次发信失败后，待验证账号仍会保留；同一邮箱再次注册时，
服务命中重复账号但不重发邮件，接口仍固定返回 `202 accepted`，导致页面错误提示“验证邮件已发送”。
生产环境目前使用阿里云 DirectMail，验证码邮件与链接邮件均按一封邮件计费，消耗相同。

咨询链路已经要求首次咨询和每次追问调用生产 Provider，并向追问传递最近对话、当前主题和已确认
事实。但 DeepSeek 连续返回无法通过结构校验的内容时，本地路由对部分通用表达无法确定主题，
异常最终会变成 `503`。这会让用户误以为系统没有理解其问题，且无法继续补充信息。

## 目标

- 注册验证改为邮件内显示的 6 位数字验证码。
- 验证码有效期固定为 10 分钟；每次重发生成新码并使旧码立即失效。
- 数据库不保存明文验证码，不新增数据库表或迁移。
- 待验证账号再次注册时实际发送新验证码。
- 应发送邮件但 DirectMail 失败时返回真实错误，前端不得再提示发送成功。
- 首次咨询和每次追问仍调用配置的生产 DeepSeek。
- 每次追问继续携带有界的最近对话、当前主题和已确认事实。
- DeepSeek 超时、网络异常、限流或连续输出无效时快速返回安全追问，不让页面长期等待或直接失去回复。
- 不因安全降级臆断纠纷类型、责任、法律结论或用户事实。
- 未登录页面明确说明登录后的真实权益，并提供直接的登录与注册入口。
- 不在日志中记录用户正文、验证码、Provider 原始输出或密钥。

## 非目标

- 密码重置邮件继续使用一次性链接。
- 不更换邮件服务商，不开通 Sendify，也不引入短信验证码。
- 不修改注册容量、用户配额、隐私政策、验证码人机校验或正式法律 Playbook。
- 不重建 PostgreSQL，不操作服务器上的其他站点或服务。

## 方案选择

### 采用：只使用数字验证码

注册邮件只展示 6 位验证码，注册页面在待验证状态显示验证码输入框和重发按钮。该方案与用户
预期一致，移动端输入简单，并且每次发送仍只消耗一封 DirectMail 邮件。

### 不采用：验证码与链接并存

双通道能兼容更多使用习惯，但会同时维护两套验证入口，扩大前端状态、安全测试和故障排查范围，
没有必要。

### 不采用：保留验证链接

改动最小，但不能解决用户希望直接填写验证码的需求。

## 认证架构

### 验证码签发

认证服务使用密码学安全随机数生成器生成从 `000000` 到 `999999` 的 6 位字符串。验证码摘要使用
从现有 `IP_HMAC_SECRET` 通过独立用途字符串派生的子密钥，对规范化邮箱和验证码计算 HMAC；只把
摘要写入现有 `auth_tokens` 表，purpose 继续使用 `email_verification`。邮箱参与摘要计算，防止
同一验证码被用于其他账号；带密钥的 HMAC 防止仅获得数据库内容的人离线枚举全部 100 万个验证码。

邮箱验证码使用独立的 10 分钟有效期，密码重置令牌继续使用现有令牌有效期。签发新验证码时调用
现有 replace-token 语义，使该用户所有尚未使用的旧邮箱验证令牌立即失效。

### 注册与重发

`POST /api/auth/register` 保持注册资料、隐私确认、CAPTCHA、容量和频率限制不变：

1. 新邮箱创建待验证账号，签发并发送新验证码。
2. 已存在的待验证账号签发并发送新验证码，解决首次邮件失败后无法重发的问题。
   重复注册不会覆盖首次提交的密码或隐私确认记录。
3. 已激活或不可注册账号继续返回不泄露账号详情的通用结果，不发送验证码。
4. 需要发送邮件时，DirectMail 失败必须抛出安全的 `mail_unavailable` 错误并返回 `503`；
   前端只在接口成功后显示“验证码已发送”。

`POST /api/auth/resend-verification` 对待验证账号执行同一签发和发送流程。服务端现有邮箱加客户端
双重频率限制继续生效；前端增加 60 秒倒计时，防止误触和连续点击。接口对不存在或已激活邮箱仍使用
通用响应，避免直接暴露账号状态。

### 验证

`POST /api/auth/verify` 接收规范化邮箱与 6 位验证码。服务端先执行格式和频率检查，再计算 HMAC
摘要并以单次消费方式激活对应待验证账号。错误、过期、已用或被重发替换的验证码统一返回
`verification_code_invalid`，不区分具体原因。

部署前已签发的旧链接不再作为新流程展示；其数据库令牌按原清理策略过期。仍处于待验证状态的用户
可在注册页面重新发送并获得数字验证码。

### 前端交互

待验证状态显示：

- 当前待验证邮箱；
- 6 位验证码输入框，使用 `inputmode="numeric"`、`autocomplete="one-time-code"` 和固定长度；
- “验证”主操作；
- 带倒计时的“重新发送”操作；
- 发送成功、验证失败、频率受限和邮件服务不可用的明确状态。

验证码只保存在当前页面内存，不写入 URL、localStorage、日志或分析事件。切换邮箱时清空输入值。
密码重置链接的 URL fragment 处理保持不变。

匿名试用条继续说明“累计 5 次纯文字咨询，且不保存历史”，并在同一区域增加
“登录后可保存历史、上传材料并使用独立额度”的权益说明和“登录”“注册”入口。
两个入口复用现有认证弹窗并直接打开对应页签，不阻断匿名试用，也不宣传系统尚未提供的能力。

## Provider 数据流

### 正常路径

首次咨询和每次追问继续通过现有 Provider 工厂选择生产 DeepSeek。追问请求上下文保持有界，只包含
完成当前判断所需的最近对话、当前案件主题、阶段和已确认事实。Provider 返回通过模型及结构校验的
结果后，现有本地路由、案件推进和渲染规则继续负责最终响应，模型不能绕过这些边界。

### Provider 故障降级

DeepSeek 超时、网络异常、限流、服务错误或结果连续无法通过 JSON、字段及业务结构校验时：

1. 记录脱敏的失败类别和请求关联 ID，不记录用户正文或模型原文。
2. 若当前会话已有案件主题和阶段，保留现有状态，不切换主题。
3. 若本地确定性规则能从当前原话识别主题，继续使用该覆盖结果。
4. 若当前原话明确命中正式 Playbook，只询问该 Playbook 首个尚缺的必填事实；覆盖结果仍保持
   `unverified_guidance/unknown`，会话不得在本轮绑定正式场景。
5. 若仍无法确定，构造通用 `unknown` 澄清结果，询问争议对象、对方具体行为和用户希望解决的问题。
6. 澄清结果不得补写用户未陈述的事实，不得指定责任或给出胜诉判断。
7. API 返回成功的安全澄清响应，不再因为 Provider 故障而让用户一直等待或没有回复。

该路径证明 DeepSeek 已被实际调用，但其输出未被系统冒充为有效答案。Provider 请求 ID 和用量保持
为空，审计记录实际失败类别并标记为 `degraded`；本轮不扣用户咨询额度。

### 降级后的上下文恢复

下一轮仍把最近对话、上轮原话和安全追问传给 DeepSeek。若上轮原话被本地确定性规则识别为正式
主题，本轮只把它作为“待确认主题提示”，不能单独据此绑定案件。只有恢复后的 DeepSeek 返回同一
正式主题、置信度达到现有门槛，且当前原话没有更强的冲突主题信号时，才进入正式 Playbook。DeepSeek
继续失败、返回其他主题或置信度不足时，保持未绑定状态。

待确认主题只从紧邻的安全降级轮次恢复，并同时核对：该轮没有 Provider 请求 ID、覆盖结果为
`unverified_guidance/unknown`，且系统问题与本地识别 Playbook 的缺失必填项一致。这样既能理解
“2000 元”一类紧接上轮问题的简短回答，也不会把普通历史对话或模型单方面猜测当成用户案件。

## 错误与安全边界

- 服务端根据邮箱和输入值计算 HMAC 摘要，再通过数据库等值查询并单次消费，不记录明文验证码。
- 验证、注册和重发均保留服务端频率限制；前端倒计时不是安全边界。
- 验证错误不暴露验证码是否过期、被替换或邮箱是否存在。
- DirectMail SDK 异常只映射为安全错误码，服务端日志不得包含 AccessKey、邮箱正文或验证码。
- Provider 故障只记录失败分类、耗时和请求 ID，不记录提示词、用户正文或原始回复。
- 本地澄清内容只能基于注册主题和安全模板生成，不能自由推断案件。

## 测试

认证测试覆盖：

- 验证码始终为包含前导零在内的 6 位数字，数据库只保存 HMAC 摘要。
- 正确验证码可激活账号；错误、过期、已使用和旧验证码均失败。
- 重发后旧码失效，新码可用，10 分钟边界准确。
- 待验证邮箱重复注册会发送新验证码。
- DirectMail 失败返回 `503 mail_unavailable`，页面不显示发送成功。
- 不存在或已激活邮箱的重发保持通用响应。
- 注册、重发、验证频率限制和账号枚举防护不回归。
- 移动端与桌面端的注册、输入、重发、登录和密码重置流程通过端到端测试。

Provider 测试覆盖：

- 首次咨询和每次追问均调用配置的 Provider。
- 追问上下文包含有界历史、当前主题和已确认事实，不包含其他用户数据。
- 超时、网络异常、限流、服务错误和无效结构均返回安全澄清响应并退款。
- 首次明确命中正式主题但 Provider 故障时询问首个必填项，覆盖仍为 `unknown`，会话不绑定场景。
- 用户回答该必填项后，只有 DeepSeek 与上轮本地主题提示一致且置信度达标才进入正式流程。
- DeepSeek 与提示冲突、置信度不足或当前消息出现新主题时不沿用旧提示。
- 已有会话在无效输出后保留主题和阶段。
- 安全降级不臆断纠纷类型且不扣咨询额度。
- 日志断言不包含用户正文、模型正文、验证码和密钥。

完成定向测试后运行全量测试、Python 编译检查、前端语法检查和 `git diff --check`。

## 发布与回滚

验证通过后构建唯一的新镜像标签，在生产服务器 `/srv/weiquan/current` 使用现有环境文件
`/etc/weiquan/weiquan.env` 更新 `weiquan-app`。发布不得重建 `weiquan-postgres`，不得操作
`/srv/audio` 或 `audio.072988.xyz`。

发布后检查容器健康状态、`/live`、`/ready`、公网 HTTPS、真实 DirectMail 验证码和一轮不含个人
敏感信息的 DeepSeek 咨询。若健康检查或核心流程失败，只把应用容器回滚到上一固定镜像；数据库
无结构变更，因此不需要数据库回滚。
