# 统一、有依据的咨询回答体验设计

## 状态

- 日期：2026-08-16
- 设计方向：用户已确认采用“DeepSeek 上下文理解 + 后端确定性法律装配 + 必要时第二次有依据成文”
- 本文状态：书面规格待用户复核
- 发布范围：仅 `weiquan-app`

## 背景

当前咨询系统在命中正式 Playbook 时，能够使用已核验规则生成较完整的方案；未命中 Playbook 或进入追问后，回答质量却会明显下降。典型表现包括：

- DeepSeek 已经识别出高置信场景，但本地关键词未命中后仍被降为未知主题；
- 用户表达诉求，例如“我希望商家重新发货”，系统把它误判成已完成上一步并机械推进阶段；
- DeepSeek 生成了针对当前问题的回答，却被静态 Guidance 阶段模板覆盖；
- 只有带问号或明显疑问词的文本才允许直接回答，陈述式诉求只能收到流程提示；
- 未命中 Playbook 的回答没有任何可靠法律依据，和正式 Playbook 的体验差距过大；
- 追问重复上一轮内容，或只说“进入第 2 步：整理证据”，没有回应用户刚刚说的话；
- Provider 异常时，本地降级内容过于泛化，用户等待较久后仍得不到可执行帮助。

问题的核心不是回答字数不足，而是当前消息没有成为本轮回答的第一优先级。系统需要先判断用户此刻是在提问、补充事实、表达诉求、报告已完成动作，还是开始了新纠纷，再决定应该回答什么、是否推进、应当装配哪些已核验依据。

## 目标

- 每一轮首先回应用户当前问题或诉求，不用流程模板代替答案。
- 首次咨询和每次追问都结合当前消息、已确认事实、当前诉求和最近有效上下文。
- 首次咨询和每次追问至少进行一次 DeepSeek 上下文理解；需要提升完整性时，在共享时限内进行第二次有依据成文。
- 正式 Playbook 继续提供本案结论、时效、金额和本案适用法条。
- 未命中 Playbook 时，在不冒充正式法律判断的前提下提供已核验的领域通用法条、具体行动和证据建议。
- 阶段推进由明确的用户行为驱动，不因轮次增加而自动推进。
- DeepSeek 超时、失败或输出不合法时，仍返回与当前纠纷和上下文有关的本地安全回答。
- 建立可自动回归的质量门槛，防止只修复少数截图中的句子。

## 非目标

- 不让 DeepSeek 自行决定正式法律结论、赔偿金额、时效或本案法条适用性。
- 不把所有未知问题强行映射到合同、消费者或其他常见法律领域。
- 不使用模型记忆直接补录法条正文、条号或发布日期。
- 不为了固定流程强制每轮调用两次，也不允许第三次生成；第二次调用只使用后端已确认的事实、规则和法条。
- 不重写既有 Playbook 的实体法律结论，除非独立核验发现原规则有误。
- 不改变账户、额度、验证码、邮件、附件或其他无关业务。
- 不重建或替换 PostgreSQL。
- 不触碰 `audio.072988.xyz`、`/srv/audio` 或其他服务。

## 用户体验契约

### 当前消息优先

回答必须先处理本轮用户实际表达，再决定是否需要重述背景。历史上下文只用于消解“他”“这个”“还是不处理”等指代、理解延续关系和避免重复，不得覆盖当前消息的明确含义。

例如，用户在“商家发错货”之后说“我希望商家重新发货”：

- 应识别为 `stated_goal`；
- 应先确认该诉求，并告诉用户如何明确要求补发、是否保留错货以及如何留痕；
- 不得把它解释为“用户已经联系商家”或“证据已整理完成”；
- 不得仅显示“进入下一步”。

### 有用回答的最小组成

正常回答至少完成以下三项中的两项，并且第一项强制满足：

1. 直接回应当前问题、陈述或诉求；
2. 给出当前就能执行的具体动作；
3. 说明需要保留的具体证据、相关已核验法律依据或一个高价值追问。

“请保留证据”“建议协商”“建议咨询专业人士”本身不算具体动作。动作必须说明对象、内容和目的，例如“通过平台聊天向商家发送补发要求，写明订单号、错发商品、希望补发的商品以及答复期限，并保存发送和已读记录”。

### 结构与篇幅

根据问题复杂度动态组织回答，不要求每轮机械显示所有栏目。推荐顺序为：

1. 直接回答；
2. 现在怎么做；
3. 重点证据；
4. 法律依据及其适用边界；
5. 一个下一问题。

简单追问可以短，但不能因为短而漏掉答案。复杂咨询的可见正文上限由约 800 个中文字符提高到约 1200 个中文字符；达到上限时优先保留直接回答、行动和安全提示，压缩背景复述及重复免责声明。

### 表达方式

面向用户只使用自然、清楚的中文，不展示 `Playbook`、`coverage`、内部阶段编号、置信度或 Provider 状态等实现术语。可以简短承接用户的焦虑、损失或目标，但不得用大段套话代替答案，也不得使用责备用户的表达。法条之后应紧跟一句通俗解释，说明它与该类纠纷可能有什么关系。

### 追问数量

每轮最多提出一个高价值问题。问题必须能够改变下一步行动、法律路径、风险等级或证据判断。已经回答过、可以从上下文推知、仅用于填满模板的问题不得再次询问。

### 禁止敷衍的判定

出现以下任一情况即视为失败：

- 没有回应当前消息，只复述上一轮或展示阶段名称；
- 把用户希望发生的事当成已经完成的事；
- 行动建议与争议对象无关或只有泛化动词；
- 用户问“为什么、能不能、怎么办”却没有明确回答；
- 在有已核验领域依据时完全不展示法律支持；
- 未核验问题被包装成确定的本案结论；
- 同一轮提出多个低价值问题，把理解成本转回给用户；
- DeepSeek 失败后只返回“请补充更多信息”而没有利用已有上下文。

## 统一轮次理解

### 结果模型

首次咨询和追问共用第一阶段的 DeepSeek 语义结果。建议引入内部结构 `TurnUnderstanding`：

```text
intent:
  stated_goal | direct_question | new_fact | completed_action |
  continue_case | more_precise_question | new_case |
  risk_changed | no_progress
case_relation:
  same_case | likely_same_case | new_case | unclear
topic_candidates:
  [{ topic_id, confidence, supporting_text }]
current_goal:
  normalized user goal or null
fact_delta:
  [{ fact_key, value, source_text, certainty }]
completed_actions:
  [{ action_id, source_text }]
answered_question:
  normalized current question or null
direct_answer_draft:
  provider draft that addresses the current message
action_suggestions:
  provider-proposed practical actions, not legal conclusions
evidence_suggestions:
  provider-proposed evidence targets
legal_issue_tags:
  controlled tags used only for backend lookup
next_question_candidate:
  one candidate or null
risk_flags:
  controlled safety flags
confidence:
  0..1
```

DeepSeek 不输出可直接采用的法条正文、条号、确定金额、时效或 `verdict`。即使模型在草稿中出现这些内容，后端也必须删除或用正式 Playbook / 已核验法条重新装配。

### 意图定义

- `stated_goal`：用户表达希望得到的结果，如退款、补发、赔偿、道歉、停止骚扰。
- `direct_question`：用户提出新的明确问题，如“我可以要求补发吗”。
- `new_fact`：用户补充会影响判断的事实，如付款方式、是否拆封、平台答复。
- `completed_action`：用户明确报告已执行某项动作及结果，如“我已经联系平台，平台拒绝了”。
- `continue_case`：用户明确要求继续当前流程，但没有新增事实或问题。
- `more_precise_question`：围绕上一轮内容提出更细问题，如“这个期限从哪天开始算”。
- `new_case`：用户明确切换到另一独立纠纷。
- `risk_changed`：人身、安全、财产损失或证据灭失风险发生变化。
- `no_progress`：只有情绪、确认词或无法可靠解析的内容，且不具备推进条件。

`direct_question` 与 `more_precise_question` 的差异只服务于上下文和去重，两者都必须直接回答。复合消息按风险变化、明确问题、完成动作、新事实、诉求的优先级提取，并允许保留次要信号，但最终只选择一个主意图。

### 上下文输入

传给 DeepSeek 的上下文按以下优先级组装：

1. 当前用户原文，明确标记为本轮最高优先级；
2. 当前纠纷主题、正式场景或未核验领域；
3. 已确认事实与当前诉求；
4. 最近若干轮有效对话摘要；
5. 已给出的行动和已问问题摘要；
6. 当前阶段和安全状态。

只纳入同一纠纷的有效上下文。已被用户纠正的事实、前端错误提示、重复模板和模型猜测不得重新注入。上下文达到长度上限时，保留当前消息、诉求和确认事实，优先删除较旧的回答全文。

## 自适应一到两次 DeepSeek 调用

### 第一阶段：上下文理解

首次咨询和每次追问都执行第一阶段。统一提示同时完成语义理解和安全回答草稿，并明确：

- 首先解释当前消息与历史纠纷的关系；
- 直接回应当前问题或诉求，不得仅输出流程状态；
- 不假设用户完成了没有明确报告的动作；
- 不重复已经展示的内容；
- 只能根据输入事实生成草稿，缺失事实使用条件式表达；
- 不编造法条、条号、金额、时效或司法结论；
- 只输出约定 JSON，不附加 Markdown 或说明文字。

首次咨询、追问、陈述式诉求和明确问句都允许产生 `direct_answer_draft`。是否有问号不再作为允许回答的门槛。

第一阶段返回后执行确定性校验：

- 枚举值、置信度、字段长度和列表数量合法；
- `supporting_text`、`source_text` 必须能在当前消息或有效上下文中定位；
- `completed_action` 必须包含完成态证据词和具体对象；
- `new_case` 必须有主题变化证据，不能仅凭低置信猜测；
- 删除草稿中的未经后端核验的条号、金额、时效和确定性结论；
- 未正式覆盖时，草稿中的“依法应当”“必然构成违法”“一定能获得”等本案确定性主张必须被替换为有事实条件的安全表达。

Provider 可以对同一响应做一次本地受控提取或解析，但不能通过重新请求模型纠正第一阶段格式。若理解结构整体无效，立即使用已有会话状态做本地降级，不在错误基础上发起第二次调用。

### 后端依据包

第一阶段之后，后端完成路由、事实确认、阶段决策、Playbook 匹配和法条分层，并生成只读的 `GroundingPacket`：

```text
current_message
turn_intent
case_summary
confirmed_facts
current_goal
completed_actions
coverage_mode
formal_findings
allowed_actions
evidence_targets
verified_statutes:
  [{ statute_id, title, article, verified_text, official_url, basis_scope }]
limitations
previously_answered
one_allowed_next_question
```

`GroundingPacket` 只包含后端允许出现在最终回答中的事实、结论和法条。没有进入依据包的法条、金额、时效或结论，即使 DeepSeek 知道或猜到也不得输出。

### 第二阶段：有依据成文

第二次 DeepSeek 调用负责把依据包组织成自然、完整、针对当前用户的最终回答。以下情况默认使用第二阶段：

- 正式 Playbook 结论需要和本轮问题、诉求或新事实合并解释；
- `domain_general` 法条需要转换为容易理解、边界清楚的说明；
- 用户提出权利、责任、金额、时效、处理路径等实质问题；
- 多轮追问需要消解指代并说明新内容与前文的关系；
- 第一次草稿或确定性装配没有同时满足直接回答、具体行动和依据/证据质量门槛；
- 回答虽然字段完整，但语言仍明显模板化、重复或没有落实用户当前目标。

以下情况可以跳过第二阶段并立即返回：

- 紧急安全路径要求立即给出确定性提示；
- `no_progress` 只需要简短确认和一个必要问题；
- 第一次草稿与后端装配已经完整通过内容质量门槛，且不需要解释法律材料；
- 共享时间预算不足或 Provider 已出现故障。

第二阶段只生成以下受控结构：

```text
direct_reply
actions
evidence
legal_explanation
limitations
next_question
used_statute_ids
```

第二阶段不得改变第一阶段意图、已确认事实、路由、阶段、`verdict`、金额、时效或法条集合；不得增加依据包之外的事实和法条；`used_statute_ids` 必须是 `GroundingPacket` 的子集。后端再次执行字段、事实、法条、确定性语气、长度和去重校验，校验通过后才可显示。

第二阶段失败或输出不合格时，不发起第三次调用。系统直接使用第一阶段有效草稿和 `GroundingPacket` 做确定性装配，保证用户仍然获得有内容的回答。

### 调用与额度边界

- 每个用户轮次至少一次、最多两次逻辑 DeepSeek 调用；
- 两次调用共享同一个端到端时间预算，不能各自完整等待一次超时；
- 第一次调用保持短而结构化，为第二次成文预留时间；
- 用户产品额度按一次咨询轮次结算，不因内部调用两次而扣两次；
- 任一次 Provider 故障导致最终本地降级时，按降级规则退还本轮额度；
- 审计记录分别标记理解调用和成文调用，便于定位耗时及质量问题。

## 语义路由仲裁

### 基本原则

DeepSeek 的高置信候选是语义证据，本地关键词是佐证和冲突检测，不再是硬否决门槛。路由仍由后端最终决定，模型不能直接选择正式 Playbook。

### 仲裁顺序

1. 先识别紧急风险和明确的新纠纷。
2. 对已有正式 Playbook 的同一纠纷，默认保持当前场景，除非当前消息有充分的新纠纷证据。
3. 对首次咨询或未核验主题，综合 DeepSeek 置信度、支持原文、本地正向关键词和冲突关键词。
4. 高置信语义候选且无实质冲突时，可进入对应候选场景的事实核验。
5. 有冲突或关键事实不足时，保持未核验领域并问一个能区分路径的问题。
6. 无可靠领域信号时保持 `unknown`，不得默认映射到合同法或消费者法。

关键词零分只表示“没有额外本地佐证”，不再自动推翻有原文依据的高置信候选。反向关键词、场景互斥事实和用户明确纠正仍可否决候选。

## 阶段推进

未核验指导的阶段不是按追问次数递增，而是按用户已经完成的动作和获得的结果推进。

| 主意图 | 默认推进 | 处理方式 |
| --- | --- | --- |
| `stated_goal` | 否 | 回应诉求，调整建议，不假定动作完成 |
| `direct_question` | 否 | 直接回答，保持当前可执行步骤 |
| `more_precise_question` | 否 | 回答细节，避免重放完整方案 |
| `new_fact` | 通常否 | 说明新事实的影响；仅在事实证明条件满足时改变路径 |
| `completed_action` | 是或转支路 | 根据动作结果进入后续步骤 |
| `continue_case` | 有条件 | 当前步骤可执行且未完成时给出更具体执行内容；已有完成证据时推进 |
| `new_case` | 新建主题 | 不污染原纠纷状态 |
| `risk_changed` | 切换安全路径 | 优先处理紧急风险 |
| `no_progress` | 否 | 简短确认并问一个最有价值的问题 |

仅发送“继续”不能伪造已完成事实。如果当前步骤尚未完成，系统应告诉用户完成这一步所需的具体内容；如果上文已经明确报告完成，则进入下一步。

## 确定性回答装配

### 装配顺序

后端 `AnswerAssembler` 使用第一阶段结果、路由、Playbook、已核验法条和会话状态先生成 `GroundingPacket` 与可直接降级使用的初步答案，再合并可选的第二阶段成文结果：

1. 选择或生成针对当前消息的直接回应；
2. 应用正式 Playbook 结论，或保留未核验边界；
3. 选择与当前诉求和阶段有关的行动；
4. 选择与争议事实有关的证据；
5. 装配允许显示的已核验法条；
6. 选择一个未问过且能改变后续路径的问题；
7. 判断是否需要第二阶段有依据成文；
8. 合并通过校验的第二阶段结果，或保留初步答案；
9. 去重、压缩并执行最终安全校验。

模型负责语义针对性和自然表达，后端始终负责法律权威性、事实边界、阶段、允许使用的依据、去重和最终输出结构。第二阶段只能在后端依据包内成文，不能反向修改后端决策。

### 直接回应来源优先级

1. 通过完整性、事实、法条和确定性边界校验的第二阶段 `direct_reply`；
2. 通过事实、确定性主张和法律边界校验的第一阶段 `direct_answer_draft`；
3. 正式 Playbook 与当前意图匹配的确定性回应；
4. 领域通用的本地安全回应；
5. `unknown` 的事实化回应，说明当前可以确定的内容和需要核对的一点。

降级回应也必须引用当前纠纷对象、用户诉求或已确认事实中的至少一项，不能只返回通用错误文字。

### 去重

延续既有“有实质进展才持久化”的原则。新回答至少满足一项：

- 回答了新的问题；
- 解释了新事实的影响；
- 确认并落实了新的诉求；
- 根据已完成动作推进；
- 给出此前未展示的具体执行内容；
- 提出一个更精确、未问过的问题；
- 响应风险变化或新纠纷。

法条标题、免责声明、阶段标签或措辞变化不构成实质进展。

## 法律依据分层

### A 层：正式本案依据

仅在正式 Playbook 成功匹配且关键事实满足时显示：

- `verdict`；
- 本案时效；
- 确定金额或计算方式；
- 标记为“本案适用”的法条；
- Playbook 中经过核验的处置路径。

DeepSeek 不得覆盖这一层。

### B 层：已核验领域通用依据

未命中正式 Playbook 但能够可靠识别领域时，可以显示本地法条库中已经通过官方来源核验的领域通用法条。展示必须同时满足：

- 法条来源是全国人大法律法规数据库、国务院、最高人民法院等相应官方来源；
- 本地记录包含法规名称、条号、核验正文、官方链接、核验日期和适用标签；
- 领域映射由后端受控标签决定，不采用模型自由文本；
- 页面明确标记“以下为该类纠纷的一般法律依据，是否适用于你的具体情况仍需结合事实核对”；
- 不输出确定 `verdict`、时效、金额或“你一定可以获得”的承诺。

例如，食品安全、网络购物、一般商品质量、经营者义务等领域可在完成官方核验后配置相应 B 层依据。法条与当前领域不匹配时宁可不显示，也不能为了“看起来专业”硬挂法条。

### C 层：暂无可靠法条

主题为 `unknown`、领域证据冲突或本地没有已核验依据时，不显示猜测法条。回答仍需提供基于事实的行动、证据建议和一个区分路径的问题，并明确当前尚不能可靠确认法律依据。

### 法条补充流程

新增法条必须经过以下步骤：

1. 根据测试用例和真实咨询缺口生成候选领域清单；
2. 只访问权威官方页面查询现行文本；
3. 对照法规名称、效力状态、条号、正文和施行日期；
4. 保存官方 URL、查询日期、适用标签和通用/正式层级；
5. 添加文本一致性测试和领域映射测试；
6. 人工抽查后才允许在用户回答中展示。

搜索引擎摘要、博客、问答网站和模型记忆只能帮助定位，不得作为法条正文来源。

## API 与前端呈现

### 响应语义

API 需要明确区分：

- `formal`：正式 Playbook 覆盖；
- `domain_general`：已核验领域通用依据；
- `unverified_guidance`：有针对性的安全指导但暂无可展示通用法条；
- `unknown`：领域尚不能可靠识别。

建议为法条增加 `basis_scope` 和 `applicability_notice`，避免前端把 B 层通用依据渲染成“本案适用法条”。前后端对合法字段组合使用同一契约和共享测试样例。

### 可见顺序

前端优先展示直接回答，随后展示行动、证据和法律依据。覆盖范围提示应清楚但不能抢占首屏，使用户等待后首先看到的仍是对自己问题的回应。

追问回答不重复整份旧方案。正式方案没有变化时，显示本轮答案和变化内容，并允许用户查看此前完整方案。

### 等待体验

- 正常路径根据完整性需要发起一到两次逻辑 DeepSeek 调用；
- 两次调用共享 30 秒 Provider 总预算，不能把两个独立超时串联成 60 秒；
- 第一阶段提示保持精简，第二阶段只接收压缩后的 `GroundingPacket`；
- 正常响应目标为中位数不高于 12 秒、95 分位不高于 28 秒；
- 共享预算耗尽后立即返回已完成的初步装配，浏览器最迟在 35 秒结束等待；
- 前端始终在成功、失败和超时分支清理加载状态；
- 降级轮次不消耗用户额度。

性能目标用于监控和回归，不表示外部网络异常时对每次请求作绝对承诺。

## Provider 故障降级

DeepSeek 超时、网络错误、限流或结构化输出异常时：

1. 保留当前会话主题、诉求、已确认事实和阶段；
2. 使用路由候选、Playbook 或领域本地模板组装针对性回答；
3. 不伪造 provider request id，不伪装成模型成功；
4. 不生成新的法律结论；
5. 退款本轮预留额度；
6. 允许用户继续追问，且下一轮仍能使用本轮有效事实；
7. 审计记录故障类别和降级路径，但不记录密钥、验证码或完整敏感正文。

如果连领域也无法可靠识别，仍应复述已理解的争议对象和诉求，并只问一个最关键问题，不得返回空内容。

## 可观测性

每轮记录不含敏感正文的结构化指标：

- 最终主意图及置信度；
- 当前消息与既有纠纷的关系；
- DeepSeek 候选、本地关键词佐证及最终路由；
- 阶段是否变化及变化原因；
- 法律依据层级和法条 ID；
- 是否触发第二阶段、采用了哪一阶段的内容、是否触发本地降级；
- Provider、装配、持久化和总耗时；
- 去重守卫是否修正输出；
- 额度最终状态。

不得在普通日志中打印 API key、认证 token、邮箱验证码、附件原文或完整对话。必要的对话排障使用受控审计 ID 定位。

## 测试策略

### 单元测试

- 九类轮次意图的正例、反例和复合消息优先级；
- 陈述式诉求可以产生直接回答；
- `stated_goal`、`direct_question` 和 `new_fact` 不自动推进；
- 只有明确 `completed_action` 或满足条件的 `continue_case` 推进；
- DeepSeek 高置信候选不会被关键词零分硬否决；
- 冲突事实仍能否决错误候选；
- 草稿中的未核验条号、金额、时效会被删除；
- 首次咨询和每次追问都会执行第一阶段上下文理解；
- 权利、责任、金额、时效和复杂追问等场景会触发第二阶段成文；
- 第二阶段只能使用 `GroundingPacket` 中的事实、结论和法条 ID；
- 第二阶段失败后使用初步答案，且绝不发起第三次生成；
- 两次调用共享截止时间，用户产品额度仍只按一轮结算；
- A/B/C 三层法条组合和 API 校验；
- B 层只能引用本地已核验官方法条；
- `unknown` 不默认挂合同法条；
- 去重守卫不会把免责声明变化当成进展；
- Provider 故障仍生成包含当前纠纷信息的本地回答。

### 对话回归

至少覆盖以下完整多轮对话：

1. “商家发错货” -> “我希望商家重新发货” -> “如果他不理我怎么办”；
2. “30 元外卖里有虫子” -> “我已经拍照但吃掉一部分” -> “可以要求多少”；
3. 用户补充新事实但法律结论不变；
4. 用户报告已联系商家并被拒绝，阶段正确推进；
5. 用户只说“继续”，系统不伪造已完成动作；
6. 用户使用“他、这个、还是不处理”等指代，回答正确联系上下文；
7. 同一会话中明确开始另一纠纷，旧事实不污染新主题；
8. 用户纠正模型此前理解，错误事实不再进入后续上下文；
9. Playbook 内问题与 Playbook 外问题的回答结构和有用性保持一致；
10. DeepSeek 超时、返回非 JSON、返回违法字段时的降级路径。

### 内容质量断言

测试不只断言字段存在，还应断言：

- 第一段包含对当前问题或诉求的回应；
- 行动中出现与纠纷相关的对象和动作；
- 没有把希望、计划误写成完成事实；
- 追问不在历史已问问题中；
- 未核验回答没有确定性赔偿承诺；
- 有 B 层映射时包含通用依据和适用边界；
- 第二阶段回答逐项覆盖依据包要求的直接回答、行动、证据和法律说明；
- 第二阶段没有擅自改变后端确定的事实、阶段、金额、时效或法条；
- 新回答与上一轮相比包含可解释的实质进展。

### 真实 Provider 与浏览器验收

自动测试通过后，使用真实 DeepSeek 对上述关键多轮对话执行验收，检查语义、延迟、上下文关联和降级指标。随后在本地浏览器分别以匿名试用和登录用户完成端到端测试，确认：

- 加载状态会结束；
- 回答顺序正确；
- 法条层级文案不会误导；
- 手机和桌面端内容不溢出、不重叠；
- 追问能够继续同一纠纷；
- 复杂回答按设计调用第二阶段，简单完整回答不会无意义追加调用；
- 两阶段路径的总等待时间不突破浏览器保护上限；
- 额度结算符合成功/降级结果。

真实 Provider 输出具有非确定性，因此验收同时检查结构约束和语义样例，不以某一句固定措辞作为唯一成功条件。

## 示例体验

用户：`商家发错货了。`

合格回答应先说明系统理解的是“收到的商品与订单不符”，再给出核对订单、拍摄商品及面单、通过平台留痕联系商家等动作；若已核验一般商品交易领域依据可用，则显示为“该类纠纷的一般法律依据”，而不是直接宣称用户必然胜诉；最后只问用户希望补发还是退款。

用户继续：`我希望商家重新发货。`

合格回答应确认“可以先把补发作为当前明确诉求”，给出一段可直接发送给商家的关键信息和留痕要求，并说明在商家拒绝或不回复时下一步如何提交平台。阶段保持不变，不得回复“进入第 2 步”。

用户继续：`如果他不理我怎么办？`

合格回答应直接解释达到什么条件后转平台、提交哪些材料、平台仍不处理时再走什么渠道；不得重新询问用户想退款还是补发，也不得重放完整首轮答案。

## 实施边界

预计改动集中于：

- DeepSeek 两阶段结构化输出、提示和共享时间预算；
- 语义路由仲裁；
- 轮次意图和阶段推进；
- Pipeline 与确定性回答装配；
- 法条模型、领域映射和种子数据；
- API 契约和前端展示；
- 单元、集成、真实 Provider 和浏览器测试。

实施时先为失败对话补回归测试，再逐层修改路由、推进、装配和法条，最后调整前端契约。每一步都必须保持既有正式 Playbook 测试通过。

## 发布与回滚

- 本地全部自动测试和真实 DeepSeek 验收通过后重启本地页面；
- 本地用户体验验收通过后，仅构建并部署 `weiquan-app`；
- 不执行会重建数据库或影响其他服务的完整部署脚本；
- 发布前确认迁移需求，能通过兼容字段完成时不做数据库迁移；
- 发布后检查健康状态、匿名试用、登录咨询、追问、额度和日志；
- 回滚只针对本次应用镜像或代码版本，不回滚用户已有数据，不操作音频服务。

## 完成标准

只有同时满足以下条件才视为完成：

- 典型失败对话和扩展多轮场景全部通过自动回归；
- 真实 DeepSeek 追问能够稳定联系上下文；
- 需要完整法律说明的轮次能在最多两次调用内形成有依据的成文回答；
- 陈述式诉求得到直接回应且不会错误推进；
- 未命中 Playbook 时仍有针对性行动和证据建议；
- 有已核验领域法条时正确显示 B 层依据及边界；
- 没有可靠法条时不猜测、不硬挂；
- Provider 故障仍能给出有内容的本地回答，并正确退款额度；
- 本地浏览器和手机尺寸验收通过；
- 线上仅更新 `weiquan-app`，发布后核心链路验证通过；
- 不出现密钥、验证码、token 或敏感对话泄漏。
